Master's Thesis Defended at FTN: Teaching Kalliope to Understand Paraphrases

A multilingual hybrid NLP module that lets an open-source voice assistant act on English and Greek commands it was never given word for word.

View source on GitHub →

This year I defended my M.Sc. thesis at the Faculty of Technical Sciences (FTN), University of Novi Sad. The full title is a mouthful: Multilingual Hybrid NLP Module for Semantic Intent Understanding in the Kalliope Voice Assistant. The idea behind it is short. A voice assistant should react to what you mean, not to the exact words you happened to use.

The work started during my Erasmus+ exchange at the University of the Peloponnese. ESDA Lab in Patras uses Kalliope, an open-source Python voice assistant, to control lights, fans, web radio, ambient sound and a handful of lab-specific actions. It worked well as long as people said things the way someone had written them into its configuration. My job was to make it understand everything else, in English and in Greek.

01 · Intent classifier: a fine-tuned transformer maps a sentence to a Kalliope synapse.
02 · Retrieval fallback: FAISS finds the closest known question when the classifier is unsure.
03 · Generative fallback: mT5-small answers queries that are outside the intent set.
04 · Final classifier (XLM-RoBERTa): 97.1% accuracy, 0.967 macro-F1.

Where phrase matching breaks

Kalliope's configuration, the "brain", is a YAML file of synapses. Each synapse has signals that trigger it and neurons that do the work: say something, run a shell command, call an API. The most common signal is an order, a phrase you expect the user to say. The default matching rule, in Kalliope's own documentation, is that a synapse fires if all words of the order are present in the spoken sentence. Stricter variants also forbid extra words or require the same word order.

That is easy to reason about, and it falls apart as soon as real people talk to it. Suppose the order for the kitchen synapse is written as turn on the kitchen lights. These are all real training sentences for that same intent from my dataset: 

Brighten up the kitchen area.
Kitchen illumination needed, please.
Let there be light in the kitchen!
Άναψε τα φώτα στην κουζίνα.

None of them contains all the words of the order. The last one shares no words with it at all, because it is Greek. To cover them with phrase matching, someone has to anticipate every phrasing and write it down, once per language. The documentation also warns that if one order is contained in another, both synapses fire, so adding more orders makes collisions more likely.

The fix I went for is to stop matching words and start classifying meaning. A model reads the sentence and outputs the name of the synapse it belongs to. Kalliope then runs that synapse directly. The brain file stays the same; only the decision of which synapse to run moves into a model.

The hybrid design

A single classifier is not enough on its own, because people also ask things that are not commands at all. So the module has three paths, and the confidence of the classifier decides which one a sentence takes.

The intent classifier is a fine-tuned transformer that maps a sentence to one of the lab's intents. Every intent label is the name of a Kalliope synapse, such as kitchen-on, fan-lab1 or run-web-radio. In the repository the gate sits at a softmax probability of 0.9: above it, the label goes straight to Kalliope.

The FAISS fallback handles sentences the classifier is unsure about. The sentence is embedded with paraphrase-multilingual-MiniLM-L12-v2 and compared against a small set of question and answer pairs about ESDA Lab. The answer stored with the closest question is spoken back.

The generative fallback is for queries that are outside the intent set entirely: small talk, questions about the assistant itself. The label map has a dedicated generative class for this, trained on sentences like "What can you do?" and "Who built you?", so the classifier itself learns to say "this is not a command". In the final thesis system those queries go to mT5-small.

The most important design decision is the one in the caption. Turning off the lights in a lab where someone is working is a worse failure than saying something unhelpful. So only the classifier, the part I could measure and trust, is allowed to run actions. Both fallbacks end in speech.

Data and training

The intent data is a set of JSONL files, one per area (lights, ambient sound, radio, web, weather, reminders, and so on). Each line is an instruction, an input sentence and a label: 

{"instruction": "Classify the intent of the following sentence.",
 "input": "Can you switch on the kitchen lights for me?",
 "output": "kitchen-on"}

The version in the repository has 1,365 examples across 15 files: 750 in English and 615 in Greek. The label map defines 50 labels, including generative. 44 of them have examples, between 17 and 60 each; the other six exist in the map but have no data yet, which I come back to at the end.

Before tokenization, each sentence goes through a small preprocessor. It lowercases and normalizes whitespace, and for text without Greek characters it strips punctuation and runs an English spell checker. Greek text is detected with a character-range check and left alone, since a spell checker built for English would only damage it.

The repository still contains the DistilBERT baseline (distilbert-base-multilingual-cased), so the training details I can show here are for that model: sequences of 64 tokens, batch size 16, learning rate 2e-5, mixed precision, trained with the Hugging Face Trainer. The logged run took about nine minutes on a single A100. The final model in the thesis is XLM-RoBERTa, and that is the one the results below refer to.

For the fallbacks, the retrieval set is 231 question and answer pairs about ESDA Lab, almost all in English. The FAISS index is a flat L2 index, so search is exact rather than approximate, which is the right call at this size. The repository's generative experiment is a GPT-2 fine-tune on the same ESDA Lab questions; the final thesis system uses mT5-small.

Results

All numbers come from the evaluation in the thesis.

Component Model Metric Result
Intent classifier XLM-RoBERTa Accuracy / macro-F1 97.1% / 0.967
Retrieval fallback MiniLM + FAISS Hit@1 / MRR 48% / 0.579
Generative fallback mT5-small Rated fully appropriate 27.9%

The classifier carries the system. 97.1% accuracy across a bilingual intent set is the number that decides whether people can actually use the assistant, and the macro-F1 of 0.967 sitting close to it means the result is not a few large intents hiding a long tail of weak ones.

The fallbacks are much weaker, and I think that is worth saying plainly instead of burying it. There are a few reasons, and they are mostly structural rather than a matter of tuning:

  • They get the hardest inputs by construction. A sentence only reaches retrieval because the classifier was unsure about it. Whatever made it ambiguous for the classifier usually makes it hard for the retriever too.
  • The retrieval set is small and English. 231 pairs cannot cover what people ask a lab assistant, and a bilingual front end feeding an English-only knowledge base will miss Greek questions that have no good English neighbor.
  • Retrieval always answers. The lookup returns the single nearest question with no distance cutoff, so a question with no real match still gets the closest wrong answer. An MRR of 0.579 against a Hit@1 of 48% also says the right entry is sometimes ranked lower down rather than first.
  • Open-ended generation with a small model is hard. mT5-small is a small model asked to do the least constrained job in the system, and 27.9% fully appropriate replies reflects that.

For the design, the conclusion is the one the architecture already encodes. The fallbacks are useful as a way to keep the conversation going, not as a source of truth, and they should never be able to trigger an action. When the system is unsure, the worst case is an unhelpful sentence, not a light switching on in an empty room.

Kalliope integration

Because every label is a synapse name, the integration is thin. Kalliope has a documented command line option, --run-synapse, that runs one named synapse from the brain. The classifier only has to produce the right name. This is the classification step from classifier.py: 

def classify(self, text: str) -> tuple[str, float]:
    input_text = f"{INTENT_PROMPT_PREFIX} {text}"
    inputs = self.tokenizer(
        input_text,
        return_tensors="pt",
        truncation=True,
        padding="max_length",
        max_length=INTENT_MAX_LENGTH,
    ).to(self.device)

    with torch.no_grad():
        logits = self.model(**inputs).logits

    probs = torch.softmax(logits, dim=1)
    class_id = torch.argmax(probs, dim=1).item()
    return id2label[class_id], probs.max().item()

And this is the gate from the interactive test loop, where a confident label is handed to Kalliope:

if confidence >= CONFIDENCE_THRESHOLD and label != "generative":
    print(f"Kalliope will now run: {label}")
    subprocess.run(["kalliope", "start", "--run-synapse", label])
    return

Everything that does not pass the gate becomes speech. The retrieval step is short, which is part of why it is easy to reason about: 

def search(self, query: str) -> str:
    query_vec = self.embedder.encode([query])
    _, indices = self.index.search(np.array(query_vec), FAISS_TOP_K)
    matched_text = self.texts[indices[0][0]]
    return self._answer_lookup.get(
        matched_text.lower(),
        f"I found something similar: {matched_text}",
    )

The returned text goes to a single say-dynamic-message synapse whose only job is to speak whatever it is given. That keeps the brain file clean: one synapse per real action, plus one for everything the assistant says on its own.

What I would do differently

Going back through the code to write this post made a few things obvious.

Keep the evaluation in the repository. The thesis numbers come from a separate evaluation, and the training script trains on everything with no evaluation split. Anyone looking at the repository alone cannot reproduce the 97.1%. Next time the split and the evaluation script live next to the training code from day one.

Use one preprocessing function for training and inference. Training lowercases, strips punctuation and spell-checks; the inference code passes raw text to the tokenizer, and with a different maximum length (128 instead of 64). The model still works, but it is seeing slightly different inputs in production than in training, and that kind of skew is cheap to prevent and annoying to debug.

Let retrieval say "I don't know". A distance threshold on the FAISS result would turn a confident wrong answer into an honest non-answer. For a lab assistant that is a better failure.

Make the knowledge base bilingual. The classifier understands Greek; the retrieval set mostly does not. The multilingual embedding model can bridge some of that gap, but Greek question and answer pairs would do it properly.

Clean up the label map and the keyword rule. Six labels have no training examples, so the classifier can never predict them. There is also a keyword override that forces the reminder intent when certain phrases appear; it includes very short Greek words like σε matched as substrings, which can fire far more often than intended. Either give the model the examples it needs or make the rule much narrower.
