RAG Retrieval Architecture

Why your LLM is usually not the bottleneck, but your retrieval layer is.

Many teams try to improve weak RAG answers by switching models. A stronger LLM can help with reasoning, formatting, instruction following, and synthesis. But it cannot reconstruct information that never reached its context window.

If the retrieval layer returns the wrong document, misses the paragraph containing the answer, drops an important qualifier, or retrieves five loosely related chunks around the right one, generation starts from a compromised state. The failure happens before the model begins answering.

Better retrieval raises the answer ceiling for every model you use. Model upgrades alone often hide weaknesses in the search layer.

That is why I tend to think about production RAG systems less as "LLM applications" and more as retrieval systems with a language model attached to the end.

RAG is a pipeline, not a vector database

A simplified RAG implementation is often presented as:

User question
     -> Embedding
     -> Vector search
     -> Top K chunks
     -> LLM
     -> Answer

That works surprisingly well for a prototype. It also hides most of the problems that appear later.

A production retrieval pipeline usually starts looking more like this:

                         +----------------------+
                         | Conversation state   |
                         +-----------+----------+
                                     |
                                     v
User question --------------> Query understanding
                                     |
                            +--------+--------+
                            |                 |
                            v                 v
                     Query rewrite      Metadata extraction
                            |                 |
                            +--------+--------+
                                     v
                            Retrieval request
                                     |
                     +---------------+---------------+
                     |                               |
                     v                               v
               Dense retrieval                Lexical retrieval
                     |                               |
                     +---------------+---------------+
                                     v
                                Fusion
                                     |
                                     v
                                Reranking
                                     |
                                     v
                           Context construction
                                     |
                                     v
                                   LLM
                                     |
                                     v
                           Grounded response

Every stage can improve the answer. Every stage can also silently destroy it.

The core failure pattern

Consider a knowledge base containing hundreds of internal documents. A user asks:

What is the reimbursement limit for employee category B under policy FIN-217?

The correct chunk contains:

Policy: FIN-217

Employee category B:
Maximum reimbursement: EUR 850 per calendar year.

A pure semantic search may return:

  1. a general travel reimbursement policy
  2. a paragraph explaining employee categories
  3. another policy containing EUR 850
  4. a related finance FAQ
  5. the introduction to FIN-217

Everything is semantically relevant. Nothing answers the question.

The generator then receives plausible context and produces a plausible answer. That is one of the more dangerous RAG failure modes because the final response does not necessarily look broken. The retrieval is approximately correct, while the answer requires something exactly correct.

Names, policy IDs, ticket numbers, dates, product codes, abbreviations, amounts, and legal terminology are particularly good at exposing this problem.

Semantic similarity is not relevance

Vector search solves an important problem: which pieces of text are semantically similar to this query?

But semantic similarity and answer relevance are not identical. Suppose the query is:

What happened to incident INC-18473?

The embedding representation captures concepts such as:

incident
problem
status
failure
resolution

That is useful. But the most important token may simply be INC-18473. A lexical search engine can recognize that exact identifier immediately. A dense embedding may treat several incident descriptions as semantically equivalent.

This is why I rarely consider pure vector search sufficient once the corpus contains structured terminology.

Hybrid retrieval

Hybrid retrieval combines two different views of relevance.

Dense retrieval

Dense embeddings are good at understanding meaning. They can connect "How much vacation do I have?" with "Annual leave entitlement" even though the wording is different.

Lexical retrieval

Keyword-based retrieval is good at exactness. It preserves:

  • names
  • identifiers
  • acronyms
  • numbers
  • uncommon terminology
  • product codes
  • policy references

A useful retrieval system benefits from both. Conceptually:

async def hybrid_search(query, top_k=10):
    dense_hits = await search_dense(
        query,
        limit=top_k * 3,
    )

    lexical_hits = await search_lexical(
        query,
        limit=top_k * 2,
    )

    combined = fuse_results(
        dense_hits,
        lexical_hits,
    )

    return combined[:top_k]

The important part is not simply running two searches. The important part is deciding how their rankings should interact.

Rank fusion

Dense and lexical engines usually return scores that are not directly comparable. A vector similarity score of 0.82 does not necessarily have any mathematical relationship with a BM25 score of 12.4. Simply adding them is often meaningless.

One approach is to normalize both score distributions. Another is to work with ranking position rather than raw score. A common conceptual approach is reciprocal rank fusion: 

score(document) =
    1 / (k + dense_rank)
    +
    1 / (k + lexical_rank)

A document that appears near the top of both rankings receives a strong combined score. This has another useful property: documents that are extremely strong in one retrieval strategy can still survive even when they rank poorly in the other. That matters for queries containing either very strong semantic intent or very specific lexical constraints.

Retrieval should produce candidates, not the final context

Another architecture mistake is treating the result of the first search as the final context, for example:

Vector DB
   -> Top 5
   -> LLM

I prefer to separate candidate retrieval from context selection.

The first stage should optimize recall. The second stage should optimize precision. Instead of retrieving exactly five chunks, the system might retrieve 30 candidate chunks from several retrieval strategies. Then a reranking stage selects the most useful: 

30 candidates
      -> reranker
      -> 5-8 final chunks

This gives the system room to recover from imperfect initial ranking.

Reranking

Embedding similarity answers approximately: are these two pieces of text about similar things?

A reranker can evaluate a much more direct question: given this exact query, how useful is this exact document for answering it? That distinction is important.

A retrieval pipeline can therefore use a relatively inexpensive first stage to reduce the corpus:

100,000 chunks
      -> retrieval
      -> 30 candidates

and then spend more computation evaluating those candidates carefully:

30 candidates
      -> cross-encoder / reranker
      -> 6 final chunks

Reranking is particularly valuable when many documents discuss almost the same subject. Imagine an HR knowledge base containing:

  • Annual Leave Policy
  • Annual Leave Manager Guide
  • Annual Leave FAQ
  • Annual Leave 2025 Update
  • Annual Leave Regional Exceptions
  • Annual Leave Payroll Instructions

All of them may have extremely high semantic similarity to "How many annual leave days do employees in Slovenia receive?" The difficult problem is no longer retrieval. It is ranking within a dense cluster of relevant-looking documents.

Metadata is part of retrieval

Not every search decision should be made using text similarity. Suppose every indexed chunk carries metadata:

{
  "country": "SI",
  "department": "HR",
  "language": "sl",
  "document_type": "policy",
  "effective_year": 2026,
  "access_level": "employee"
}

A query may imply some of these constraints:

What is the current Slovenian annual leave policy?

There is little reason to retrieve a Croatian policy from 2024 and hope the reranker removes it later. The retrieval request can be constrained first: 

country = SI
effective_year = 2026
document_type = policy

and then semantic and lexical ranking can operate inside that smaller candidate set. This is not only a performance optimization. It is part of relevance.

Metadata filtering vs semantic filtering

These should not be confused.

Semantic retrieval asks: which documents discuss this concept?

Metadata filtering asks: which documents are even eligible to answer this question?

For example, "How do I request maternity leave?" may require semantic retrieval. But "How do I request maternity leave in Serbia?" contains both a semantic intent (maternity leave procedure) and a metadata constraint (country = Serbia). Treating both parts as embedding text wastes structure that is already available. A good retrieval pipeline separates them.

Chunking is part of the retrieval model

Chunking is often treated as preprocessing. In practice, chunk boundaries define the objects your search engine is capable of retrieving. That makes chunking part of the retrieval architecture.

Consider this paragraph:

Employees may work remotely for up to three days per week.

Employees working from another country require written approval
from HR and the employee's department manager.

Requests exceeding 30 consecutive days must additionally be
reviewed by Legal.

If the text is split badly:

Chunk A:
Employees may work remotely for up to three days per week.
Employees working from another country require

Chunk B:
written approval from HR and the employee's department manager.
Requests exceeding 30 consecutive days...

a query about international remote work may retrieve only one half of the rule. The model receives an incomplete fact. No generation prompt can repair that reliably.

Fixed-length chunking is convenient, not intelligent

A naive implementation might do:

for i in range(0, len(text), 800):
    chunks.append(text[i:i + 800])

It is fast. It also ignores structure. Better chunking should try to preserve boundaries such as:

  • headings
  • paragraphs
  • sentences
  • table rows
  • FAQ question-answer pairs
  • numbered procedures
  • policy sections

A simple structure-aware implementation might conceptually look like:

def chunk_sections(sections, max_chars=1200):
    chunks = []

    for section in sections:
        if len(section.text) <= max_chars:
            chunks.append(section)
        else:
            chunks.extend(
                split_by_sentence(section)
            )

    return chunks

The correct strategy depends heavily on the document type. An FAQ and a legal policy should not necessarily use the same chunker.

Overlap helps, until it does not

Chunk overlap is useful when relevant information crosses a boundary. For example:

Chunk 1:
AAAA BBBB CCCC DDDD

Chunk 2:
CCCC DDDD EEEE FFFF

The repeated region prevents connected facts from becoming completely separated. But excessive overlap has consequences. It can produce several near-identical retrieval results: 

result 1 -> paragraph A + paragraph B
result 2 -> paragraph B + paragraph C
result 3 -> paragraph C + paragraph D

Now three of the top results may contain mostly duplicated text. This reduces context diversity and wastes tokens. Overlap should therefore be treated as a parameter that affects retrieval quality, not as a universally good setting.

Parent and child retrieval

Sometimes the best unit for search is not the best unit for generation. A small chunk may be excellent for retrieval:

Remote work outside the country requires HR approval.

But the LLM may need the surrounding policy section to understand:

  • exceptions
  • duration limits
  • approval hierarchy
  • effective dates

One useful pattern is:

small child chunks
      -> search
      -> retrieve matching child
      -> expand to parent section
      -> LLM context

This gives the embedding model precise search units while preserving broader context during generation.

Tables need different treatment

Tables are particularly easy to destroy during ingestion. Consider:

CountryMax remote daysApproval
Serbia30HR
Slovenia60Manager + HR

Flattening this poorly might produce:

Country Max remote days Approval Serbia 30 HR Slovenia 60 Manager HR

The relationships still exist for a human. They are much less explicit for retrieval. A better representation can serialize each row independently: 

Country: Serbia
Maximum remote-work duration: 30 days
Approval required: HR
Country: Slovenia
Maximum remote-work duration: 60 days
Approval required: Manager and HR

Retrieval architecture starts during ingestion. If the index contains ambiguous representations, no search algorithm will completely fix them later.

Query rewriting

Retrieval systems rarely receive clean standalone questions. Users speak conversationally. Consider:

User:
What is our relocation policy for Germany?

Assistant:
...

User:
And what about France?

The second query is "And what about France?" Embedding that literally loses most of the useful intent. Before retrieval, it can be rewritten into "What is our relocation policy for France?" Now the query contains a meaningful retrieval target.

Query rewriting should be conservative

There is also a failure mode on the other side. An LLM used for query rewriting can accidentally change the user's intent.

The original query:

Can contractors receive the relocation allowance?

should not become:

What relocation allowance do contractors receive?

The rewrite has silently assumed eligibility. A good rewrite should improve searchability while preserving uncertainty. Conceptually:

rewritten = rewrite_query(
    current_question=query,
    conversation=history,
    rules=[
        "preserve user intent",
        "resolve pronouns",
        "restore omitted entities",
        "do not assume facts",
    ],
)

The query rewriting model is part of the retrieval system. It deserves evaluation just like the search engine does.

Sometimes one query is not enough

Some questions contain multiple retrieval requirements. For example:

Compare parental leave in Serbia and Slovenia and tell me which policy changed most recently.

This can be decomposed into subqueries:

1. Current parental leave policy Serbia
2. Current parental leave policy Slovenia
3. Effective dates / revision history

Each query can retrieve independently. The final context can then be assembled from all three result sets. This works particularly well for:

  • comparisons
  • multi-entity questions
  • procedures with several steps
  • questions spanning multiple document types

The alternative is hoping one embedding vector represents every dimension of a complex query equally well. Often it does not.

Retrieval is also an access-control boundary

Enterprise RAG adds another constraint: a relevant document is not necessarily an allowed document.

Imagine retrieval returns a perfect answer from a manager-only compensation document to a regular employee. From a ranking perspective, the system worked perfectly. From a system-design perspective, it failed completely.

Authorization therefore needs to happen before restricted content reaches generation. Conceptually:

User
 -> Resolve identity / role
 -> Determine access scope
 -> Retrieve only allowed documents
 -> Rerank
 -> Generate

Filtering the final answer is too late. Once unauthorized content has entered the model context, the security boundary has already been crossed.

Freshness matters

Enterprise knowledge changes. Policies are updated. Prices change. Contacts move. Documentation becomes obsolete.

Without version and validity metadata, the retriever may confidently return an older document simply because it matches the wording better. Useful metadata might include: 

created_at
updated_at
effective_from
effective_until
version
is_active
supersedes

The retrieval system can then distinguish a highly similar old document from a slightly less similar current policy. For many business questions, the second one is clearly more relevant.

Context construction

Even after reranking, retrieval is not finished. Suppose the system selected six chunks. The next question is: how should those chunks be presented to the model?

Simply concatenating everything works, but context quality can often be improved. I generally want each chunk to preserve useful provenance:

[Document]
HR_Remote_Work_Policy_2026.pdf

[Section]
International Remote Work

[Content]
Employees working outside their registered country...

This helps in several ways. The model can distinguish separate sources. Citation generation becomes easier. Conflicting documents become visible. Debugging becomes far easier because we can inspect exactly what information the model received.

Do not stuff the context window

Larger context windows create a tempting strategy: retrieve more. That is not always better.

Suppose the correct answer appears in chunk 2. If you provide 2 relevant chunks, the signal is strong. If you provide 2 relevant chunks plus 18 loosely related chunks, you have increased the amount of information while reducing the relative importance of the answer.

The objective should not be to maximize retrieved tokens. It should be to maximize useful evidence per token. This is another reason why reranking and deduplication matter.

Deduplication

A search index often contains near-duplicates. Examples include:

  • document revisions
  • copied SharePoint pages
  • repeated headers
  • translated copies
  • overlapping chunks
  • generated summaries
  • archived versions

Without deduplication, the top results can become:

1. Policy paragraph
2. Almost identical policy paragraph
3. Same paragraph from older document
4. Same paragraph with overlap
5. Related FAQ

The retriever appears confident because the same information dominates the ranking. In reality, the context has poor diversity. Deduplication can happen using document IDs, parent IDs, normalized text hashes, semantic similarity, or version metadata, depending on the ingestion architecture.

Retrieval confidence is not answer confidence

Another useful distinction: retrieval confidence and answer confidence are different things.

If every retrieved result has weak relevance, the correct system behaviour may be:

I could not find enough information in the available documents.

That is usually better than forcing the LLM to synthesize an answer from weak evidence. A retrieval pipeline can expose signals such as:

top score
score distribution
reranker score
number of supporting sources
agreement between retrieval methods

These can inform whether generation should proceed normally, request clarification, or refuse to make a grounded claim.

The "no result" path matters

A surprisingly important RAG capability is being able to return nothing.

If the system always produces five chunks, even for completely unrelated questions, the LLM will always receive something. Consider: what is the company's policy for working from Mars?

A nearest-neighbour database will still have nearest neighbours. That does not make them relevant. The system needs a path like:

query
 -> retrieval
 -> insufficient evidence
 -> "No supporting information found"

instead of:

query
 -> retrieve unrelated text
 -> LLM improvisation

Abstention is part of retrieval quality.

Evaluate retrieval separately from generation

If the final answer is wrong, there are at least two major possibilities.

Retrieval failure

The correct evidence never reached the model.

Generation failure

The correct evidence was retrieved, but the model interpreted or expressed it incorrectly.

These require completely different fixes. Changing the prompt will not repair missing retrieval. Changing the embedding model will not repair an LLM that ignores explicit context. That is why I prefer evaluating retrieval independently.

Recall@K

One of the simplest useful metrics is Recall@K. Suppose you have 100 evaluation questions with known relevant documents.

If the correct source appears somewhere in the top 5 results for 91 questions:

Recall@5 = 0.91

This answers: how often does retrieval provide the generator with a chance to answer correctly? If Recall@K is poor, generation tuning is premature.

Mean Reciprocal Rank

Recall tells you whether the correct result appeared. It does not tell you where. Consider two systems.

System A

1. Correct result
2. ...
3. ...

System B

1. ...
2. ...
3. ...
4. ...
5. Correct result

Both may have identical Recall@5. System A is still preferable. Mean Reciprocal Rank gives more credit when the first relevant result appears higher:

RR = 1 / rank

so:

rank 1 -> 1.00
rank 2 -> 0.50
rank 5 -> 0.20

Averaging reciprocal rank across the evaluation set gives MRR.

Build a retrieval test set

You cannot reliably optimize retrieval by clicking through a chatbot. I prefer a fixed evaluation dataset containing cases such as:

{
  "query": "What is policy FIN-217?",
  "relevant_documents": ["FIN-217"],
  "expected_entities": ["850 EUR", "category B"]
}

The dataset should include more than easy semantic questions. Add queries involving:

  • exact IDs
  • person names
  • abbreviations
  • misspellings
  • multilingual wording
  • follow-up questions
  • multiple documents
  • outdated policies
  • queries that should return no result

Then every architectural change can be compared against the same baseline.

Evaluate by query type

A single aggregate score can hide important regressions. Imagine a system achieves:

Recall@5 = 92%

That sounds good. But splitting by query type might show:

General semantic questions        98%
Exact identifier queries          71%
Person-name queries               84%
Follow-up conversational queries  76%

Now the architecture problem becomes much clearer. You might not need a new embedding model at all. You may need:

  • lexical retrieval for IDs
  • entity-aware search for names
  • query rewriting for follow-ups

Evaluation should tell you what to change.

Debug the retrieval trace

When an answer is wrong, I want to see something like:

ORIGINAL QUERY
"What about the Slovenian version?"

REWRITTEN QUERY
"What is the Slovenian remote work policy?"

FILTERS
country = SI
document_type = policy

DENSE RESULTS
1. Remote Work Policy SI
2. Hybrid Work FAQ SI
3. Remote Work Policy RS

LEXICAL RESULTS
1. Remote Work Policy SI
2. Slovenian Employment Guide

FUSED RESULTS
...

RERANKED RESULTS
...

FINAL CONTEXT
...

Without this trace, debugging RAG quickly becomes guessing. You see the final answer but not the decisions that produced it. Production observability should expose the retrieval pipeline, not only model latency and token usage.

Latency is an architecture constraint

A theoretically excellent pipeline can still be unusable if it adds:

query rewrite       900 ms
dense retrieval     300 ms
keyword retrieval   200 ms
reranker           1600 ms
LLM generation     3000 ms

Now the user waits six seconds. So retrieval quality has to be balanced against latency. Useful techniques include:

  • run dense and lexical search concurrently
  • avoid rewriting already-complete queries
  • cache embeddings
  • cache stable retrieval results where appropriate
  • rerank only a bounded candidate set
  • use smaller models for routing and rewriting
  • skip unnecessary stages for simple exact queries

The best retrieval pipeline is not necessarily the one with the most components. It is the one that applies the right components to the right queries.

Route queries before searching

Not every request needs the same retrieval strategy. Consider:

"What is FIN-217?" — this may be predominantly lexical.

"How does our company handle extended remote work?" — this may benefit more from semantic retrieval.

"Compare the German and French policies." — this may need decomposition.

"Thanks!" — this may need no retrieval at all.

A mature RAG system can classify query intent before launching an expensive retrieval pipeline. Conceptually:

route = classify_query(query)

if route == "exact_lookup":
    return lexical_first(query)

if route == "semantic":
    return hybrid_search(query)

if route == "comparison":
    return multi_query_search(query)

if route == "conversation":
    return no_retrieval()

This is often more effective than forcing every query through one universal search strategy.

Multilingual retrieval adds another layer

Multilingual enterprise systems introduce a subtle problem. The user may ask in Serbian:

Koliko dana godišnjeg odmora imam?

while the source document is in English: Annual leave entitlement.

A multilingual embedding model may bridge this gap well. Keyword retrieval cannot, unless the corpus or query is normalized appropriately.

Now imagine the query also contains POL-184. Translation should preserve that identifier exactly.

A multilingual retrieval pipeline therefore has to balance:

  • cross-language semantic similarity
  • exact lexical terms
  • language metadata
  • entity preservation
  • possibly translated or rewritten queries

This is another case where hybrid retrieval becomes more useful than treating embeddings as the entire search architecture.

Embedding models matter, but later than people think

Embedding quality absolutely matters. Different models behave differently across languages, domains, short queries, long documents, code, and technical terminology.

But I would rarely make the embedding model my first tuning target. Before swapping embeddings, I would verify:

Are documents chunked correctly?
Are exact terms searchable?
Are filters correct?
Are old documents excluded?
Are follow-up queries rewritten?
Are relevant candidates reranked?
Is the evaluation set representative?

A better embedding model cannot compensate for a broken ingestion or retrieval architecture.

Generation is the last stage

Only after retrieval works well do I focus heavily on generation. At that point the prompt can tell the model to:

  • answer only from retrieved context
  • distinguish conflicting sources
  • cite the supporting document
  • state when evidence is insufficient
  • preserve numbers and identifiers exactly
  • avoid inferring unsupported facts

This can improve reliability considerably. But it works because the evidence is already good. Prompt engineering should refine a strong retrieval pipeline, not compensate for a weak one.

A practical debugging order

When a RAG answer is bad, I usually would not start by touching the LLM. I would inspect the system roughly in this order:

1. Was the answer present in the source corpus?

If not, this is a knowledge problem.

2. Was the correct source indexed?

If not, this is an ingestion problem.

3. Was the correct chunk created?

If not, this is a parsing or chunking problem.

4. Did retrieval return that chunk?

If not, this is a search problem.

5. Did the reranker keep it?

If not, this is a ranking problem.

6. Was it included in the final context?

If not, this is a context-construction problem.

7. Did the LLM receive the correct evidence and still answer incorrectly?

Only now is it primarily a generation problem.

This distinction saves a lot of pointless model and prompt experimentation.

What I measure

For retrieval itself:

Recall@K
MRR
Precision@K
nDCG

For system behaviour:

retrieval latency
reranking latency
context size
duplicate rate
no-result rate
filter accuracy

For the final RAG answer:

answer correctness
groundedness
source correctness
citation accuracy
answer completeness

The important part is keeping these layers separate. Otherwise a single "answer quality" score tells you very little about where the system is failing.

What usually improves RAG the most

In practice, the largest improvements often come from fairly unglamorous changes:

better document parsing
better chunk boundaries
hybrid retrieval
metadata filtering
query rewriting
reranking
removing stale documents
deduplicating results
better evaluation data

None of these involve replacing the main LLM. That is exactly the point. The quality of the final answer is bounded by the quality of the evidence that reaches it.

Retrieval quality sets the ceiling

A powerful language model can make poor evidence sound convincing. That is not an advantage.

In knowledge-intensive applications, I want the opposite behaviour. I want the retrieval system to make the evidence precise enough that the generation step becomes almost boring. The ideal context already contains:

  • the right document
  • the right section
  • the right version
  • the exact number
  • the necessary qualifiers
  • enough neighbouring context to interpret it correctly

Then the LLM's job is primarily to turn evidence into a useful answer.

Takeaway

RAG quality is not primarily determined by how large the language model is. It is determined by how reliably the system can move from what the user meant to the smallest set of evidence needed to answer correctly.

That requires more than embeddings. It requires good ingestion, structure-aware chunking, hybrid search, metadata, query understanding, reranking, deduplication, access control, freshness handling, context construction, abstention, and evaluation.

A useful way to think about the full system is:

Understand the query
        -> Find broad candidates
        -> Preserve exact signals
        -> Filter impossible candidates
        -> Rank by actual relevance
        -> Construct clean evidence
        -> Check whether evidence is sufficient
        -> Generate

If the retrieval layer is strong, model upgrades tend to make a good system better. If retrieval is weak, model upgrades mostly make the failure sound more fluent.

Improve search first. Then optimize generation.
