Before AI: Building a Biometric Access Controller in C

An early embedded systems project built around a PIC18 microcontroller, serial communication, and a fingerprint sensor.

View source on GitHub →

Most of my recent work lives several abstraction layers above the hardware. LLMs, computer vision systems, and Python services make it easy to forget what eventually sits underneath all of that. This project comes from an earlier stage, when the problem was much more literal: send bytes to a fingerprint sensor, wait for the right bytes to come back, and decide whether a user should be let through.

An early smart-house project

This was built around a Microchip PIC18F87K22, as an authentication layer for a small smart-house prototype. The idea was that access to alarm and device controls would sit behind a fingerprint check instead of, or in addition to, a password.

I want to be direct about what the repository actually contains, because that is the point of writing about it now. The fingerprint communication and comparison logic are the most developed part of the project and they work as implemented. Alarm control and several fingerprint-management operations are incomplete, some of them commented out entirely. That split between what got finished and what stayed a stub is not something to hide behind a cleaner retelling. It is most of the story.

Hardware architecture

The system sits between two serial links, with the microcontroller in the middle:

Terminal / User
     |
     | EUSART1
     v
PIC18F87K22
     |
     | EUSART2
     v
Fingerprint Module

EUSART1 faces the user side: a terminal sends simple text input and reads back menu prompts. EUSART2 faces the fingerprint module and carries the sensor's own command protocol. The microcontroller's job is to sit in the middle, translate one side's requests into the other side's protocol, and translate the response back.

Bytes have no meaning

UART sends bytes. It has no concept of a fingerprint, a user, a command, or a result, that meaning has to be built entirely at the application layer. The fingerprint module used here does that with a small tagged text protocol: commands look like <C>CompareFingerprint</C> and responses look like <R>...</R>.

The firmware builds a command string, writes it out one character at a time over EUSART2, then blocks until the sensor answers. Here is the actual send loop from main.c: 

char s2[30];
strcpy(s2, "<C>CompareFingerprint</C>");

for (uint8_t i = 0; i < strlen(s2); i++) {
    EUSART2_Write(s2[i]);
}

while (!EUSART2_is_rx_ready());

Nothing here knows what a fingerprint is. It knows how to push characters onto a wire and how to wait for characters to come back. Everything past that, deciding that <R>FAIL</R> means try again and a string starting with <R>PASS means let the user in, is reconstructed by the application from a raw receive buffer.

Fingerprint authentication flow

The implemented comparison path looks like this:

User requests authentication
        |
        v
Prompt for fingerprint
        |
        v
Send CompareFingerprint command
        |
        v
Wait for sensor
        |
        v
Parse result
        |
   +----+----+
   |         |
 Matched    No match
   |         |
   v         v
  Menu      Retry
             |
             v
      Reject after 3

The firmware keeps a simple attempt counter and allows up to three failed comparisons before giving up and reporting that the limit was reached. That is worth naming precisely: it is basic application-level retry logic layered over a hardware command protocol, not an access-control security model. There is no lockout timer, no logging, and no protection against someone just power-cycling the board and trying again. It does exactly one thing, cap the number of consecutive tries, and it does that one thing correctly.

The protocol was larger than the implementation

The fingerprint module's own command reference, listakomandi.txt, lists considerably more than what the firmware ended up using: 

<C>RegisterFingerprint</C>         register a new fingerprint
<C>RegisterOneFp=xxx</C>            register into a specific slot
<C>CompareFingerprint</C>           compare against stored fingerprints
<C>CheckRegisteredNo</C>            number of fingerprints registered
<C>ClearOneFp=xxx</C>               delete one fingerprint
<C>UnlockComparePWD=sss</C>         unlock via password instead
<C>SetPWD=sss</C> / <C>ClearPWD</C>  set or clear that password
<C>UnlockTimeout=d</C>              configure unlock timeout

(that notes file has a stray missing bracket on one of the lines, which feels about right for a first pass at documenting a protocol.)

Registering a fingerprint, counting registered fingerprints, and deleting one all exist as commands the sensor understands. In main.c they exist too, but as commented-out functions: regFingerprints(), checknoFingerprints(), and deleteFingerprint() are written out, with a rough retry structure sketched in, and then left disabled. The menu that is supposed to call them, fingerprintsOptions(), prints its three options and reads a selection, but each case in the switch statement is empty besides the commented-out call it was meant to make.

Device capability and application functionality are not the same thing. The sensor could register and delete fingerprints. The firmware, as it stands, could not.

Authentication before control

The intended shape of the whole system was:

Unauthorized state
        |
        v
Fingerprint authentication
        |
        v
Authorized state
        |
        v
Alarm / fingerprint administration

Once authenticated, the menu offers Turn Alarm ON, Turn Alarm OFF, and Fingerprints Options. It is worth being precise about what those first two options actually do: they print a confirmation string and nothing else. There is no GPIO write, no relay control, no actuator path behind them. The menu and the intended control flow are real and present in the repository. The physical alarm control is not. I'd rather say that plainly than let the menu screen imply more than the firmware delivers.

Working with Microchip Code Configurator

The repository includes a mcc_generated_files/ directory: device configuration, EUSART1 and EUSART2 drivers, interrupt management, and system initialization, all generated through Microchip Code Configurator rather than hand-written register by register. 

MCC-generated hardware layer
        |
        v
EUSART drivers / interrupt manager
        |
        v
Application C code (main.c)
        |
        v
Fingerprint protocol
        |
        v
Access-control behaviour

The value of that generated layer is fairly ordinary but easy to underrate: I did not have to hand-set every configuration bit on a PIC18F87K22 to get two EUSART peripherals talking, MCC generated that initialization and driver code from the peripheral selections in the GUI, and the application code sits entirely on top of it. It is a small, unglamorous example of the same layering idea that shows up everywhere in software, just one level closer to silicon.

Blocking embedded code

The firmware is full of lines shaped like this:

while (!EUSART2_is_rx_ready());

The CPU sits in that loop doing nothing until the fingerprint module answers. For a small prototype this is about as simple as serial code gets, there is no interrupt handler to reason about, no shared state, no race condition between a receive callback and the main loop. The cost is equally simple: the processor cannot do anything else while it waits, and if the sensor never answers, the program is stuck there indefinitely. I would not call this a mistake so much as a common first shape for embedded code, the one you write before you have a reason to write the other kind.

What I would change today

None of this is a rewrite of the historical code, the repository stays as it is. But looking at it now, a few things would change.

I would model the application as an explicit state machine instead of a sequence of blocking calls: 

IDLE
  -> WAITING_FOR_AUTH
  -> WAITING_FOR_SENSOR
  -> AUTHORIZED
  or REJECTED

I would replace indefinite blocking waits with interrupt-driven UART reception into ring buffers, and give every peripheral operation an explicit timeout instead of a while(!ready); that never gives up. And I would stop embedding raw protocol strings in application code and put the fingerprint protocol behind a small driver interface: 

fingerprint_compare()
fingerprint_register()
fingerprint_delete()
fingerprint_count()

with a real parser behind it for <C>...</C> and <R>...</R>, one that checks buffer bounds, handles a malformed response instead of assuming well-formed input, and returns a clear status code rather than a raw string to compare against. The whole thing would separate more cleanly into layers: 

app/
    access_control.c
    alarm.c

drivers/
    fingerprint.c
    fingerprint.h

protocol/
    fingerprint_protocol.c

platform/
    uart.c

And I would be more honest, in the design itself, about how far this is from real access-control security. A serious version would need to think about sensor trust, spoofing, how and where biometric templates are stored, privilege boundaries between authentication and administration commands, physical tampering, and what the system does when it fails, not just when it succeeds. None of that is implemented here, and I would not want to imply otherwise by staying quiet about it.

Looking back

The point of this project is not that an old embedded prototype is somehow more advanced than my current work. It is that it exercised a different layer of engineering entirely. Modern AI systems are built behind increasingly powerful abstractions: a framework handles the batching, a library handles the retries, an API handles the network. In this project there were very few abstractions left. A command was a string of bytes I built by hand. A response meant checking a receive buffer myself. A sensor that did not answer could stop the entire program. That makes ideas like protocols, timeouts, state machines, and retries very hard to treat as abstract, because at this level they are the whole job.

The scale is completely different now, message protocols between services instead of between a microcontroller and a sensor, unreliable components that are cloud APIs instead of UART lines, retries and timeouts and graceful failure at the level of a distributed system instead of a single board. But the engineering questions underneath, what happens when the other side does not answer, how do you know a response actually means what you think it means, are the same questions, just asked at a different layer.

A lot changed after that. The usefulness of understanding the layers underneath the software did not.
